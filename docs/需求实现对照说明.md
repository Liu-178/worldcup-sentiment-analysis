# 需求实现对照说明

配套文档：[世界杯舆情可视化分析系统-软件需求说明书.docx](./世界杯舆情可视化分析系统-软件需求说明书.docx)

本文档不是对需求说明书的修订。原始需求文档保持原样，一个字未改——它记录的是 2026 年 7 月开发启动时的真实设想。本文档做的是另一件事：把「当初计划做什么」和「最后交付了什么」逐条摆在一起。

---

## 先说结论

需求说明书 V1.0 定义了 **8 个页面级功能**，实际交付情况：

| 状态 | 数量 | 编号 |
|------|------|------|
| 完整实现 | 2 | 3.1 系统首页、3.4 行业词频分析（核心部分） |
| 部分实现 | 1 | 3.3 赛事热度分析 |
| 未实现 | 5 | 3.2 管理员登录、3.5 新闻检索、3.6 / 3.7 / 3.8 管理后台 |

另有 **1 项需求文档未提及的功能**（AI 对话助手）在开发后期加入。

也就是说：需求文档写的是一个带管理后台的完整 B/S 系统，实际交付的是一个聚焦分析链路的展示型站点。**这个差距在需求文档第 3 章可以直观看出来——8 个「功能界面」小节写的都是同一句「（此处预留界面截图位置）」，因为设计阶段还没做界面，也就没有截图可贴。**

## 一、逐项对照

### 3.1 系统首页 — 完整实现

| 需求要点 | 实现情况 |
|----------|----------|
| 顶部导航栏，含热度分析 / 词频分析 / 新闻检索三个入口 | 已实现，入口为：首页概览 / 对比分析 / 词云展示 / AI 助手。**「新闻检索」入口替换为「AI 助手」** |
| 项目简介、双赛季核心结论概览、五大行业热度总览卡片 | 已实现：四个核心指标卡 + 行业分布环形图 + 两届热度柱状图 + 洞察结论区 |
| 点击导航跳转 | 已实现 |
| 赛季切换按钮（2022 / 2026 / 双赛季对比三种视图） | **未实现独立切换器**，改为同页并列展示双赛季数据，减少一次点击 |
| 底部团队信息与后台入口 | 团队信息已呈现；**后台入口未做**（无后台） |

### 3.2 管理员登录页面 — 未实现

需求定义了账号/密码输入、空值与错误提示五种异常消息、登录成功跳转后台。

实际系统**没有任何登录环节，全部页面匿名可访问**。原因见第五节。

### 3.3 赛事热度分析页面 — 部分实现

| 需求要点 | 实现情况 |
|----------|----------|
| 左侧行业筛选栏，勾选五大行业 | 未实现筛选控件，改为全行业一次性呈现 |
| 热度趋势折线图，横轴日期、纵轴热度，双赛季叠加 | **未实现折线趋势图**。后端已有 `/api/timeline_stats`、`/api/daily_total` 两个时序接口，但前端未接入 |
| 鼠标悬停查看具体数值 | 已实现（ECharts tooltip） |
| 日度 / 周度统计维度切换 | 未实现 |
| 行业热度排名，标注最高时段与核心事件 | 部分实现：有行业占比排序，**未做「核心事件」标注** |

已交付的 `/compare` 页面实际形态是：行业占比横向条形对比 + 两届环形图 + 情感构成 + 多维雷达对比。**它回答的是「哪个行业更热」，需求里问的是「热度在时间轴上怎么变化」——后者没做。**

### 3.4 行业词频分析页面 — 核心部分实现

| 需求要点 | 实现情况 |
|----------|----------|
| 顶部选择赛季、行业 | 已实现（赛季切换；行业维度通过后端统计覆盖） |
| 词云图，字号对应频次 | 已实现，两届各生成独立词云 |
| 词云 / 柱状图切换，查看 Top20 频次 | 已实现（TOP20 排行 + 柱状呈现） |
| 点击关键词跳转新闻检索 | **未实现**（无检索页可跳） |

这是 8 项需求中完成度最高的一项，也是项目演示时最有说服力的部分。

### 3.5 新闻检索页面 — 未实现

需求定义了条件区（关键词 + 赛季 + 行业 + 时间范围）、结果列表、排序、展开全文、分页五项。

实际状态：后端写了 `/api/search` 和 `/api/news_list` 两个接口，**但没有任何页面调用它们**。`/chat` 页有个搜索框，输入后拼接成 `搜索：xxx` 递给 AI 问答接口，走的是大模型而不是本地检索。两者不是一回事。

### 3.6 / 3.7 / 3.8 管理后台 — 全部未实现

| 编号 | 需求内容 | 实际替代方案 |
|------|----------|--------------|
| 3.6 爬虫任务管理 | 网页上新建任务、配参数、看状态、暂停/停止、看错误日志 | 命令行执行 `python spider/world_cup_spider.py`，日志输出到控制台 |
| 3.7 数据处理管理 | 网页上执行去重、清洗、分词、词频统计、导出 CSV | 命令行执行 `python update_all.py`，一条命令串完 |
| 3.8 可视化配置 | 网页上配置配色、展示维度、默认行业、预览生效 | 无，样式写在模板里，改需动代码 |

三项需求本质是「把命令行操作搬进浏览器」。功能本身全部具备，缺的是那层 Web 界面。

## 二、需求之外新增：AI 对话助手

需求说明书全文未提及此功能。开发后期接入 SiliconFlow 的 Qwen 模型，实现了基于项目数据的问答。

它的实际作用比看起来大：需求里「新闻检索」和「数据解读」两项意图，部分被这个页面承接了——用户可以直接问「2022 年餐饮行业热度如何」，不必自己在下拉框里筛。

需要注意：**该功能依赖外部 API Key，未配置时不可用**（页面会给出明确提示）。提交版本中原有的 Key 已作废，新 Key 需自行在 `.env` 中配置。

## 三、非功能性需求对照

### 4.1 浏览器兼容性

需求：Chrome、FireFox、Edge 上布局与交互一致。

实际情况：**仅在 Edge（Chromium 内核）完成实测**，Chrome 同内核理论上一致，FireFox 未测试。没有做过多浏览器回归，不宣称完全满足。

### 4.2 性能要求

| 需求指标 | 实际情况 |
|----------|----------|
| 90% 页面 2 秒内响应 | 未做系统压测。当前数据量下本地访问为即时响应，图表渲染约 1 秒内完成 |
| 支持万级数据存储与检索 | **未验证**。实际数据 1343 条，距离万级差一个数量级；检索逻辑为 pandas 全表过滤，未做索引优化 |
| 关键词检索 3 秒内返回 | 未测（检索界面未做） |

这三项属于「设计时按完整系统定标准，交付时规模没到那个量级」，如实标注为未验证，比填一个好看的数字更可靠。

## 四、后端已实现但前端未接入的接口

开发过程中先写接口、后写页面的顺序，留下 5 个「有逻辑、没入口」的接口：

| 接口 | 功能 | 状态 |
|------|------|------|
| `/api/timeline_stats` | 按时间聚合的热度趋势 | 已实现，未接入 |
| `/api/daily_total` | 日度新闻总量 | 已实现，未接入 |
| `/api/news_list` | 新闻列表分页 | 已实现，未接入 |
| `/api/search` | 关键词检索 | 已实现，未接入 |
| `/api/sentiment_analysis` | 情感倾向分析 | 已实现，未接入 |

它们不是死代码那么简单——**3.3 的折线趋势、3.5 的新闻检索，后端其实已经写好了，缺的只是前端页面**。这也是后续补齐成本最低的切入点。

实际被前端调用的接口共 8 个：`overview`、`industry_stats`、`industry_comparison`、`industry_sentiment`、`radar_data`、`word_freq`、`industry_keywords`、`chat`。

## 五、为什么会有这个差距

按影响程度排：

1. **课时与人力**。这是小学期课程项目，需求文档按「完整舆情平台」的标准写，包含了权限体系、任务调度、可视化配置这类通常要一个团队做一两个月的内容。实际投入远小于此。

2. **管理后台的成本被低估**。三个后台页面看起来只是「操作搬上网页」，但要做得像样，需要用户体系、会话管理、任务状态持久化、异步执行与轮询。这部分工作量比前四个展示页面加起来还大。

3. **数据规模限制**。原始设想是万级数据、实时同步，实际采集 1343 条公开新闻已能说明问题，继续扩量的边际收益不高，于是把精力从「多加数据」转向「把已有数据讲清楚」。

4. **需求写在实现之前，本身就会超前**。这不完全是缺点——先想清楚要做什么，再决定砍哪些，比一开始只写「能做的」更有取舍依据。问题在于砍完之后没有回头更新文档。

## 六、如果要补齐，建议的路线

按性价比排序，前三项每项约半天可完成：

1. **接入 `/api/timeline_stats`**，在对比页增加折线趋势图 —— 直接补齐需求 3.3 的缺口，后端已就绪
2. **做一个检索页**，接 `/api/search` + `/api/news_list` —— 补齐需求 3.5，后端已就绪
3. **给需求文档第 3 章补真实截图** —— 把 8 处占位符换成实际界面，文档立刻可用
4. **管理后台**（3.6-3.8）—— 投入大，除非有明确要求，否则建议维持命令行方案，在 README 说明运行方式即可

第 1、2 项做完，需求实现率会从 2/8 变成 4/8，且都是用户可见的功能，不是纸面数字。
